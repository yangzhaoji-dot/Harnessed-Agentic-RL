# Research Paper Watch — 2026-09-20

## 1. An Empirical Study of Harness Design for Coding Agents
- **arXiv:** 2609.20804 (submitted 2026-09-17)
- **Link:** https://arxiv.org/abs/2609.20804
- **Why it matters:** Fixes the agent loop and varies three harness components—planning, action space, and context management—across 176 matched settings, four models, SWE-Bench Verified, and Terminal-Bench 2.1. The effect of each component is conditional on model capability and context budget rather than universally positive.
- **Key implication for Adaptive Harness:** This is direct empirical support for treating harness configuration as **model- and state/budget-dependent**, not as a static always-on scaffold. Planning shifts from an accuracy scaffold for weaker models toward mainly a cost-saving device for stronger models; structured tools help weaker bash users more than stronger ones; context management matters most under tight context budgets. This strengthens the case for measuring component-level marginal utility before designing adaptive intervention rules.
- **Caveat:** Evidence is from coding/terminal agents, so it should be used as a harness-design prior, not as direct evidence for ALFWorld/WebShop or creative agents.

## 2. SoL-Pi: Recursively Scaling Auto-Research Loops for Efficient Agent Harness
- **arXiv:** 2609.20519 (submitted 2026-09-17)
- **Link:** https://arxiv.org/abs/2609.20519
- **Code:** https://github.com/NVlabs/SoL-Pi
- **Why it matters:** Uses large-scale recursive auto-research over many harness rollouts to discover reusable harness changes. Four surviving mechanisms span action execution, context compaction, observation handling, and delegated reading; the resulting harness keeps performance comparable while reducing recorded token traffic by roughly 45–49% and API cost by about one third.
- **Key implication for Adaptive Harness:** It reinforces that harness optimization should treat **cost/budget as a first-class objective**, and that useful harness changes can transfer across tasks/models. For our direction, the main distinction remains that we care about **training-time adaptation, component-level credit, and internalization/externalization**, rather than only selecting a cheaper fixed runtime harness.
- **Caveat:** Primarily coding-agent / harness-search work; not Agentic RL and not a direct collision with the proposed training-signal-driven Adaptive Harness method.

## Takeaway for current direction
The strongest new signal is not another new trigger heuristic. It is that component utility is demonstrably **conditional** on model strength and resource regime. A cleaner framing for the current project is therefore:

> estimate or infer the marginal utility of individual harness components under the current policy/state/budget, then adapt the harness configuration without requiring a separately trained harness controller.

This also suggests a concrete first experiment: hold the base policy fixed and measure per-component deltas for `Plan / Reflect / Verify` across policy checkpoints and trajectory states before adding any adaptive rule.
